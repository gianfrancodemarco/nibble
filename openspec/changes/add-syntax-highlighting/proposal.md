# Proposal

## Why

Code in the reader is highlighted by one generic heuristic: a single regex
with Go, TypeScript and Python keywords mixed into one set, applied to every
line regardless of what file it came from. It gets real code wrong in ways a
reviewer notices — `#fff` in CSS becomes a comment, `#` anywhere in a Go or
TS line eats the rest of the line, a Python triple-quoted string or a Go raw
string loses its string color after the first line, and YAML, JSON, Markdown
and shell get treated as if they were C-family code. The roadmap's v0.2 item
promises the opposite: code in the drawer highlighted per language, reading
like it does in an editor.

## What Changes

- The reader learns the language of each code surface from the file path it
  already has (`/api/code` and `/api/ledger` both return `path`) and
  highlights through a vendored, pinned highlight.js bundle — battle-tested
  grammars instead of one global keyword set.
- The vendored bundle is upstream's standard common-languages build, a
  single official file fetched verbatim at a pinned version by a committed
  script. The reader's own path→language map curates what is used — Go,
  TypeScript/JavaScript, Python, JSON, YAML, Markdown, shell, CSS,
  HTML/XML, SQL. Unknown languages fall back to plain escaped text, no
  coloring.
- Highlighting is stateful across the lines of one excerpt: each contiguous
  excerpt is highlighted whole, so block comments (`/* … */`), Go raw
  strings and Python triple-quoted strings keep their color on every line
  they span; elided gaps reset the state.
- Every surface that renders code lines uses the same highlighter: the code
  drawer, the ledger drawer, and the compare visual's ref panes.
- highlight.js token classes map onto the reader's existing theme variables
  (`--kw`, `--fn`, `--str`, `--num`, `--cm`); no new colors, both themes
  keep working.
- The reader's "no runtime deps" claim becomes "minimal dependencies"
  everywhere it is made (ui-shell spec, reader/package.json): the vendored
  bundle is a committed static asset — still no npm runtime dependency, no
  bundler, and `go install` still needs no Node.

## Capabilities

### New Capabilities

None.

### Modified Capabilities

- `reader/ui-shell`: the code drawer gains per-language syntax highlighting —
  language resolved from the served file path, multi-line constructs
  highlighted across lines, a plain-text fallback for unknown languages, the
  same rendering on every code surface the shell draws (drawer, ledger
  drawer, compare ref panes) — and the build requirement's "no runtime deps"
  is restated as minimal dependencies: vendored, pinned static assets are
  allowed alongside the compiled `app.js`.

## Impact

- New vendored asset `cli/internal/cmd/ui/highlight.min.js` (BSD-3-Clause,
  license header kept), generated by a new pinned-version script under
  `reader/scripts/`, embedded by the existing `go:embed ui` and served next
  to `app.js`; `index.html` gains its script tag.
- `reader/src/visual/host.ts` — the current `highlightCode`, its global
  keyword set and `hlEsc` are replaced by a new pure module.
- New `reader/src/highlight.ts` (language-from-path resolution, whole-excerpt
  highlighting, per-line HTML splitting) plus `reader/test/highlight.test.ts`;
  both join the `files` lists in `reader/tsconfig.json` and
  `reader/test/tsconfig.json`; the node test runner loads the vendored
  bundle so tests exercise the real grammars.
- `reader/src/app.ts` (drawer, ledger drawer) and `reader/src/visual/compare.ts`
  (ref panes) switch to the path-aware API.
- `style.css` maps highlight.js token classes onto the existing theme
  variables.
- Committed build outputs regenerate: `cli/internal/cmd/ui/app.js`, and the
  site copies under `docs/visuals/` (live demo page gains the vendor script
  tag too).
- No Go code, protocol or API changes: the `path` field the server already
  serves is enough, and the embed directive already covers the ui directory.

## Out of Scope

- Languages beyond the reader's path→language map (C/C++/Java/Rust/Ruby/PHP
  and the rest fall back to plain escaped text, even where the upstream
  bundle happens to carry a grammar).
- Semantic or parser-grade highlighting beyond what the vendored grammars do
  (no type-aware coloring, no bracket matching).
- Diff coloring (added/removed line backgrounds) — the drawer's existing
  in-range emphasis is untouched.
- Highlighting code fenced inside nibble markdown titles/descriptions; the
  tiny-markdown `code` style stays as is.
- Any server-side change: language detection lives in the reader.
- A custom highlight.js theme: token classes map onto the existing five
  color variables only.

For agents

Everything in this guide is built on four commands and a folder of plain JSON.

The skill

An agent learns nibble from a skill, not from this page. One command installs it into the current repo:

$ nibble setup                                                      # installs .claude/skills/nibble/

The skill ships inside the binary: a SKILL.md that teaches Claude Code when a plate is worth building, how to write titles, descriptions, visuals and refs, the budgets, and how to answer the review — plus worked example visuals. The examples are real protocol JSON, linted by nibble's own test suite, and the skill's worked transcript is executed as a test, so the prose cannot drift from the commands. Re-running setup upgrades the installed copy; it owns only that one directory. Other agents (--agent) come with v0.2.

The CLI

The full contract (formats, the ref grammar, fingerprint and trust rules, every error code) is in PROTOCOL.md. The golden fixtures are its executable conformance suite.

$ nibble new   --title "PR 1247 · ch 1: payments" --about pr:1247   # prints the plate path
$ nibble add   <plate> --title "…" --visual timeline.json \
               --ref "src/cache/prices.ts:43-45 @cache"
✗ rejected: src/cache/prices.ts has 41 lines, ref ends at 45      # validation is strict, errors are fix-its
$ nibble done  <plate>                                              # seals it; coverage gaps reported
$ nibble lint  <visual.json>                                        # validate a visual standalone
$ nibble serve <plate>                                              # blocks; exits with your review

serve prints one reader: http://127.0.0.1:… line to stderr. The agent relays that link to the human, then sleeps until the review comes back as its exit code.

The CLI reports results through exit codes: 0 ok · 1 validation error · 2 usage. serve encodes the review: 0 done (no comments) · 2 comments to handle · 5 timeout. The full reference is in cli/README.md.

The serve command

$ nibble serve <plate> [--timeout 2h] [--addr 127.0.0.1:4000] [--no-ui] [--json]

While it blocks, serve hosts the reader on loopback. The port is random unless --addr pins one, and --no-ui waits headless. The review can come from the reader or from any tool that writes review.json; both go through the same code path. Behind the page there is a small JSON API. The reader is pure presentation, and all protocol work stays server-side:

endpointdoes
GET /api/plateheader + nibbles, every ref with trust already computed against the code as it is now
GET /api/code?n=2&ref=0the drawer: referenced lines ±3 context, diff sides resolved through git, at the trust-resolved position
POST /api/reviewwrites review.json atomically; a plate takes one review (409 review.exists)
GET /api/eventsSSE (nibble, sealed, review), so an open reader follows a plate that is still being written

Serving degrades per ref, depending on what the machine has. The plate’s repo may be absolute or relative to the plate folder:

git repo

Everything works: live trust and code for every ref kind.

just files

Plain and @worktree refs are fully verified. base..head refs read unverified, because they need git.

nothing

Text and visuals still open, every ref is unverified, and the review loop still works.

The rules

Plates live in ~/.nibble/plates

They are keyed by repo and commit, so your repos stay clean. nibble export copies one into a repo to share it.

Budgets

Titles are limited to 40 words, descriptions to 100 (overview) and 250 (standard), and plates to 7 nibbles (12 for a PR-range plate). These are budgets, not hard walls: going over needs --because, and the reason is printed on the plate for you to judge.

No pixels

Agents declare what things are, plus semantic hints (group, tier, focus, ring). nibble draws everything, so the same idea always looks the same.

An agent's explanation you can poke.

nibble turns what an agent wants to tell you — a bug, a plan, a PR — into an interactive visual model of your code, served in small nibbles. This PRD is interactive too: step the loop, turn the detail dial, filter the requirements, read the decision log.

§3

Opinionated on purpose

These are product decisions, not settings. The CLI enforces them with fix-it messages.

01Picture first, prose last

Every nibble leads with a visual. The title is one or two sentences, never a paragraph; depth lives in the levelled description (overview ≤ 100 words, standard ≤ 250). No visual, no nibble.

02Interactive, not animated

A visual you can only watch is a video. Every visual has something to do: scrub, toggle, click, step, compare.

03One canvas per plate

Nibbles move a camera across one shared map. You build a spatial picture, not a slideshow.

04Code is evidence, on demand

Click any node, edge or moment to open the validated lines behind it in a drawer.

05Small by default

Budgets that scale with the task, not walls: ~5 nibbles for a bug, maybe 12 for a big PR chapter. Going over needs a stated reason, printed on the plate for you to judge.

06The human holds the pen

A plate you asked for opens itself — you were waiting for it. A plate the agent volunteered waits in the tray until you open it. The agent can never advance or close one.

07Disagree on the thing itself

Comments pin to a node, an edge, a moment or a line — never to "the explanation".

08No themes, no knobs

Agents say what things are — including semantic hints: groups, tiers, a focus node. Never colours or pixels: nibble computes every position, so the same idea always looks the same.

09Detail is a dial

Overview, standard, deep — layers on the same canvas, never a different document. This is how plates stay small without hiding anything. Try it below.

10Visuals are cheap, so ask

Maps and compares are auto-generated. Missing a picture? Press v on the thing itself and the agent draws it in place.

§7.1

Three ways in

Same loop, three sources — in priority order: PR review first, explaining system parts and request flows just below it, local changes after.

"walk me through one checkout request, end to end"

  • System parts, request flows, flows in general — on the shared canvas
  • Auto-generated map from the import graph, a sequence stepping the request, a timeline for behaviour over time
  • Refs: path:start-end, validated and fingerprinted
$ nibble new --title "One checkout request, end to end"

"walk me through what you just changed"

  • A plate about the uncommitted diff
  • Map of touched files coloured by churn, one compare per claim
  • Refs: diff:path@worktree, validated against both sides
$ nibble new --title "What I changed and why" --about worktree

"review PR #1247"

  • Agent fetches base..head, proposes chapters if it is big, you agree first
  • Map with three rings: changed · dependents that did not change (callers, importers, tests, configs) · the rest; unvisited dependents are badged
  • Every plate ends with a not-shown ledger: the hunks no nibble referenced, open to comments
  • Refs: diff:path@base..head:start-end; comments name the side and line
$ nibble new --title "PR 1247 · ch 1: payments" --about pr:1247

§6

Visual vocabulary

Seven typed kinds; the agent writes structure, nibble draws it and wires the controls. The mockups page has a live timeline you can scrub. Visuals are auto-generated by default — a map from the import graph, a compare from the diff — and you can request new ones on demand with v.

P0map

Services and modules. Click a node for code, highlight a path.

P0sequence

Messages between actors. Step one by one, branch.

P0timeline

Events on one clock. Scrub time, toggle the fix.

P0compare

Before vs after. Drag the slider, flip.

P1state

A state machine. Fire events, spot unreachable states.

P1data

The shape of data as it moves. Follow one value.

P1chart

Numbers. Hover values; toggle what-if states the agent precomputed.

§6.2

Detail is a dial

nibble's central mechanism: it resolves the tension between small plates and real tasks, because depth grows in place instead of in a longer document. Same canvas, same camera — the dial only changes how much is drawn. Overview and standard ship with the plate; deep can be generated on demand through the same loop as a comment. Skim to decide whether to care, read at standard, interrogate at deep — a ninety-second review and a ten-minute one are the same plate.

The visual with its controls and refs. This is what a plate opens at.

    §9

    The components

    Five pieces plus one future one. The CLI is the centre: agents talk to it, plates live under it, the reader renders only what it computed.

    nibble CLI v0.1

    The single Go binary agents shell out to: new · add · done · serve · lint · export · setup. Owns all protocol logic — ref validation, fingerprints, budgets, schema checks, trust — and serve hosts the loopback server and blocks until your answer.

    Agent skill v0.1

    What setup installs into Claude Code / Codex / Cursor: when to reach for nibble, how to write titles, descriptions and visuals (worked examples), the budgets, how to answer visual requests. Prompt content, not code — the CLI enforces what the skill teaches.

    Reader v0.1

    The TypeScript SPA: canvas and camera, the visual kinds, detail dial, code drawer, comments. Pure presentation — it never touches files, it renders what the CLI computed. Embedded into the CLI binary at build time.

    Pill v1

    The thin Tauri shell: a menu-bar icon and a floating pill listing waiting plates, opening the same reader in its own window. The only component that is a desktop app.

    Protocol v0.1

    The contract everything shares: plate folder format, visual JSON Schemas, the fingerprint and trust rules, golden files. Components can be rewritten against it without breaking a single plate.

    Editor panel later

    A VS Code / Cursor webview wrapping the same reader, talking to the same CLI server, with a status-bar item as a second tray. Where the #1 use case (PR review) already lives.

    §8.3 · §9

    On disk, and the CLI

    A plate is a folder of small JSON files, append-only while open, readable by anything, versioned from day one. Refs store a fingerprint of the lines they point at; when a file changes underneath a plate, elements come back as exact, shifted or stale instead of silently wrong. Shipped: the protocol is specified in protocol/PROTOCOL.md, with JSON Schemas, golden conformance fixtures, and a tested Go package implementing it.

    Decided (2026-11-01): the CLI is a single static Go binary (small, instant start, easy installs); the reader stays TypeScript but is pure presentation. All protocol logic — fingerprints, ref parsing, budgets, validation, trust — lives once, in Go: the reader talks only to the Go server and receives trust badges already computed, never files to check. TS types are generated from the JSON Schema files, so nothing protocol-shaped is hand-written twice. Shipped: the Go CLI (new · add · done · lint · serve) and the reader — serve hosts it on loopback, computes trust per request, streams new nibbles over SSE and turns the submitted review into its exit code; the four v1 visual kinds (map · sequence · timeline · compare) render as interactive SVG with anchors wired to the code drawer and to comments, and the reader's visual types are generated from the JSON Schemas; the Claude Code skill (skill/, installed by nibble setup) teaches an agent the loop, with worked examples kept lint-clean by CI; the detail dial — visuals layer with a per-element level hint, and the reader flips between overview and standard (d) on one unmoving canvas; levelled text — plates and nibbles carry a title plus a two-depth description the dial switches with everything else; blast-radius rings — map nodes declare ring (changed · dependent · rest, all-or-nothing, computed by the agent), the reader draws three concentric zones and badges every dependent you haven't looked at, counting them down on the dependents ring; and the not-shown ledger — nibble done is now the coverage check: it diffs the code via git, matches every hunk against every ref, writes ledger.json and seals, done --check previews the misses while the plate still takes nibbles, and the reader ends every diff plate with the ledger card — each unshown hunk opens in the drawer and takes comments (ledger:path:lines). That completes the v0.1 scope; v0.2 opens with UI improvement & design adherence.

    # what the agent runs — most of the time the skill does, not you
$ nibble new   --title "PR 1247 · ch 1: payments" --about pr:1247    # prints the plate path
$ nibble add   <plate> --title "…" --visual timeline.json \
               --ref "src/cache/prices.ts:43-45 @cache"               # validated, or bounced with a fix-it
$ nibble done  <plate>                                               # coverage check, seals the plate
$ nibble serve <plate>                                               # tray + block until you answer

    §11

    MVP (v0.1)

    In: CLI (new, add, done, serve) with validation C1–C4 + C7, plate format v1, PR review (--about pr:N) and --about worktree with diff refs, reader R1–R7 + R12 (dial at overview/standard), R14, R16–R17 (blast-radius rings, not-shown ledger) with map, sequence, timeline and compare, browser-tab reader, Claude Code skill.

    Out, queued for v0.2: chapter flow for huge PRs, voice walk, the deep layer and visuals on demand, what-ifs, state/data/chart, export, editor panel, telemetry.

    Why a browser tab and not a native window: the product is interactive SVG, and the browser is its best runtime — nibble serve starts a loopback server (ephemeral port, token URL), serves the reader SPA from the binary, streams nibbles over SSE, takes comments back over POST, then writes review.json and exits with the verdict code, which is what wakes the agent. Same bundle embeds in a VS Code/Cursor panel later. Decided (2026-11-01): v1 ships a thin Tauri shell around that same web app — a menu-bar icon and a floating pill for waiting plates — so volunteered plates get a deck-calm tray while the reader stays pure web.

    §12

    Success metrics

    Interaction rate ≥ 60%

    Share of nibbles where a control was used (scrub, toggle, click). If people only press next, the visuals aren't earning their place.

    Comments on visuals

    Share of plates with ≥ 1 comment pinned to a node, edge or moment — not just to code lines.

    Agents can follow the rules

    Share of add calls rejected, and share fixed on retry.

    The whiteboard test

    "I could redraw this system afterwards." Plus median open-to-submit time by plate size.

    §10

    nibble vs deck

    deck is the closest prior art and a good product. We share its plumbing on purpose and bet differently on the medium.

    decknibble
    Primary mediumCode, narration lighting it line by lineVisual model, code as evidence on demand
    Reader's roleFollow a guided walkExplore and manipulate: scrub, toggle, what-if
    StructureSequence of groupsCamera across one canvas; ≤ 7 nibbles
    DetailOne tellingA dial: overview / standard / deep
    ScopeExplain, plan, review via the walkExplain · review the worktree · review a PR, with diff refs first-class
    NarrationProse band, read aloudTitle ≤ 40 words + levelled description (≤ 100 / ≤ 250); voice walk planned (R15)
    RuntimeNative Rust windowWeb reader in a thin Tauri shell (native pill); editor panel later
    Protocol.deck folders, frozen v1Own format only — no deck interop (decided)
    Kept from deck, with credit: the agent writes through a shell CLI, refs are validated at write time, the human opens the plate, and a blocking command returns the review. Those are the right mechanics for the category; the bet we change is the medium.

    §13

    Decision log

    Every open question from the draft is settled. All decided 2026-11-01 unless noted.

    Auto-open

    A plate you asked for opens itself; a volunteered one waits in the pill. The agent never advances or closes one.

    Tray: Tauri pill

    v1 ships a thin Tauri shell — menu-bar icon + floating pill — around the same web reader.

    Map layout: hints

    Agents give semantic hints (groups, tiers, a focus node); nibble computes every pixel.

    What-ifs: precomputed states

    Toggles between agent-precomputed curves. Continuous sliders (and DSL vs sandboxed JS) only if dogfooding demands them.

    CLI: Go

    Single static binary holding all protocol logic; the reader is pure presentation, its types generated from the schemas.

    Plates: ~/.nibble

    Global, keyed by repo + commit; repos stay clean. nibble export writes a chosen plate into a repo to share it.

    No deck interop

    Own format only (2026-10-31); deck credited for the mechanics we keep.

    The name's home: GitHub

    npm and crates.io are taken, but a Go binary doesn't need either. nibble lives at github.com/gianfrancodemarco/nibble — repo, Pages site, go install, future brew tap. No domain (2026-11-01).

    §naming

    Why "nibble"

    A small bite, and in computing half a byte. It describes how the product works — take something big in small pieces — and reads naturally as a verb: nibble through the PR. Tagline: "nibble: so you can ruminate." Also considered: ruminate, bitesize, bites, crumbs, chew, morsels, dose, capsule.
